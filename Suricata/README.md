# Suricata Network IDS: Closing the Network Visibility Gap

## Overview

This project deploys Suricata — an open-source network intrusion detection system — on the Docker host, directly addressing a gap identified in the lateral movement project: the pivot step (a TCP connection from the DVWA container to the Juice Shop container) generated zero Wazuh alerts, because host-based log monitoring has no native visibility into container-to-container network traffic. Suricata closes this gap by inspecting raw packets in real time on the Docker bridge interfaces, independent of any log file or application behaviour.

This project also demonstrates a fundamentally different detection paradigm to everything built previously: where Wazuh operates on structured log data after the fact (host-based, log-correlation), Suricata operates directly on network packets in real time (network-based, signature-matching). Understanding both approaches — and when each is appropriate — is a core detection engineering competency.

## Why Network-Level Detection Complements Host-Based Monitoring

Host-based monitoring (Wazuh agents) sees:
- What happens on a machine — file changes, process execution, authentication events
- Log data generated by applications running on that host
- Events that applications choose to log

Network-based monitoring (Suricata) sees:
- Raw packet content regardless of whether any application logs it
- Traffic between hosts that never touches a log file
- Protocol-level anomalies invisible to host agents
- Container-to-container traffic that bypasses host-level logging entirely

The lateral movement project demonstrated this blind spot directly: DVWA's web shell executed commands, accessed `/etc/passwd`, and established a TCP connection to Juice Shop — all while Wazuh's host agent saw nothing until a log volume mount was added. Suricata would have caught the network traffic regardless, since it inspects packets before they reach any application.

## Architecture

Suricata runs directly on the **Docker host** (not in a container), monitoring the Docker bridge interfaces where all inter-container traffic flows. Its structured JSON alert output (`eve.json`) is collected by the existing Wazuh agent, feeding into the same dashboard as all host-based alerts — creating a unified view of both network and host-level detections.

```
Container traffic
      ↓
Docker bridge interfaces (docker0, br-c2sim, br-dnstunnel)
      ↓
Suricata (52,000+ ET signatures, real-time packet inspection)
      ↓
/var/log/suricata/eve.json (structured JSON alert log)
      ↓
Wazuh agent (localfile, log_format: json)
      ↓
Wazuh dashboard (unified view alongside host-based alerts)
```

**Three interfaces monitored simultaneously:**
- `docker0` — DVWA and Juice Shop (web shell/lateral movement traffic)
- `br-2e1fb8921359` (c2sim-net) — C2 beacon simulator traffic
- `br-420cf65e547b` (dnstunnel-net) — DNS tunnel simulator traffic

## Installation and Configuration

Suricata was installed from the official stable PPA:
```bash
sudo add-apt-repository ppa:oisf/suricata-stable -y
sudo apt install suricata -y
sudo suricata-update
```

`suricata-update` downloaded the **Emerging Threats Open ruleset** — 52,238 community-maintained signatures covering malware C2, exploit traffic, scanning, protocol anomalies, and more. Zero custom rules were written for this project; the community ruleset was immediately productive.

**Key configuration changes to `/etc/suricata/suricata.yaml`:**

HOME_NET updated to cover all Docker subnets:
```yaml
HOME_NET: "[172.17.0.0/16,172.18.0.0/16,172.19.0.0/16,192.168.137.0/24]"
```

All three Docker bridge interfaces added to the af-packet capture section:
```yaml
af-packet:
  - interface: docker0
  - interface: br-2e1fb8921359
  - interface: br-420cf65e547b
```

Wazuh agent configured to ingest eve.json:
```xml
<ossec_config>
  <localfile>
    <log_format>json</log_format>
    <location>/var/log/suricata/eve.json</location>
  </localfile>
</ossec_config>
```

No custom Wazuh rules were needed — Wazuh ships with built-in support for Suricata's eve.json format (rule group starting at 86xxx), automatically parsing and displaying Suricata alerts in the dashboard.

## Results

### Finding 1: C2 Beacon Detected via Network Signature — Independently of Log Correlation

Within seconds of Suricata starting, **rule 2034635 "ET INFO Python BaseHTTP ServerBanner"** began firing at consistent ~15 second intervals:

```
08/07/2026-10:44:09  [**] [1:2034635:4] ET INFO Python BaseHTTP ServerBanner
[Classification: Misc activity] [Priority: 3]
{TCP} 172.18.0.2:8000 -> 172.18.0.3:48528
```

This is the C2 beacon simulator's Python HTTP server responding to check-ins from the beacon client. Suricata detected it not via timing correlation (the approach used in the Wazuh beaconing project) but via the **Python BaseHTTP server's response banner** — a string in the HTTP response header that the Emerging Threats ruleset flags as notable, since a Python HTTP server responding to internal connections at regular intervals is anomalous in most environments.

**The corroboration finding:** the same C2 activity was now being detected by two completely independent mechanisms:
- **Wazuh rule 100031** (log-correlation): detected the beaconing pattern via timing regularity in the C2 server's log file
- **Suricata rule 2034635** (network signature): detected the same activity via the HTTP response banner on the wire

In the Wazuh dashboard, both alert types appear side by side — `86601` (Suricata) and `100030/100031` (custom Wazuh rules) — both from `docker-host`, both timestamped within seconds of each other. This multi-source corroboration is exactly what builds high-confidence alerts in a real SOC: when two independent detection mechanisms catch the same thing, the confidence that it's real (not a false positive) is significantly higher than either signal alone.


### Finding 2: Rich Metadata in Suricata Alerts via eve.json

The rule 86601 alert detail in Wazuh shows the full enriched metadata from Suricata's eve.json:

- `data.in_iface: br-2e1fb8921359` — identifies the specific Docker network the traffic crossed
- `data.src_ip: 172.18.0.2`, `data.src_port: 8000` — the C2 server container specifically
- `data.app_proto: http` — protocol confirmed at application layer
- `data.alert.signature_id: 2034635` — the specific ET rule
- `data.alert.metadata.confidence: High` — ET's own confidence rating
- `data.alert.metadata.attack_target: Client_Endpoint` — confirms this is C2 client-side detection
- `data.alert.metadata.affected_product` — platform targeting metadata from the rule author

This structured, queryable metadata goes far beyond a simple alert string — every field is filterable in the Wazuh dashboard, enabling precise pivot queries ("show me all Suricata alerts on this specific interface in the last hour").

### Finding 3: Web Shell HTTP Traffic Captured in eve.json

Suricata's HTTP logging captured every web shell request in structured form in eve.json, including the full URL with command parameter:

```json
{
  "event_type": "http",
  "src_ip": "192.168.137.1",
  "dest_ip": "172.17.0.2",
  "http": {
    "url": "/hackable/uploads/shell.php?cmd=cat+/etc/passwd",
    "http_method": "GET",
    "status": 200,
    "length": 398
  }
}
```

This provides **network-level evidence of web shell usage independent of the Apache access log** — even if the volume mount had not been configured, Suricata would still have captured the `?cmd=` parameters from the wire. The combination of Suricata HTTP logging (network) and Apache access log (host/application) gives redundant, corroborating visibility into the same attack traffic.


### Finding 4: The Pivot Step — Still Unalerted

The container-to-container TCP connection (DVWA → Juice Shop, the pivot step from the lateral movement project) appeared in eve.json as a flow event with `alerted: false` — Suricata saw the connection but no ET signature matched it, since it's a plain TCP connection on a common port (3000) with no malicious-looking payload.

This is an honest, important limitation: **not all lateral movement generates network-level signatures**. A TCP connection test, a ping, or an SMB session to a legitimate-looking port won't automatically match community rules. Detecting this kind of traffic requires either custom signatures (tuned to your specific environment's baseline) or network baseline analysis (flagging connections between hosts that have never communicated before) — both beyond the scope of an out-of-the-box community ruleset. Documented as identified follow-up work: writing a custom Suricata rule to alert on new container-to-container connections on the Docker bridge.

## The Scalability Point

The architecture demonstrated here — Suricata on a network interface, eve.json into a SIEM — scales directly from three Docker bridges to an enterprise network with minimal conceptual change:

| This lab | Enterprise equivalent |
|---|---|
| Docker bridge interfaces | Physical/virtual switch SPAN ports, TAP devices |
| 3 interfaces monitored | Dozens of network segments |
| Community ET ruleset | ET Pro + custom org-specific rules |
| Single Wazuh manager | SIEM cluster |
| Manual rule updates (`suricata-update`) | Automated scheduled updates |

The detection logic, alert format, and SIEM integration are identical at any scale — only the deployment complexity changes.

## Limitations and Follow-Up Work

- The container-to-container pivot connection generated no Suricata alert — community rules don't cover plain TCP connections between internal hosts. A custom Suricata rule targeting new inter-container connections on the Docker bridge would close this specific gap
- External traffic (Windows host → DVWA container) crosses the Docker bridge and is visible to Suricata, but traffic that never leaves a container (loopback, inter-process) is not captured
- No Suricata rules were written for DNS tunneling traffic — the ET ruleset did not fire on the `tunnel.local` domain queries, since they use a private/non-routable domain that doesn't appear in any threat intelligence feed. A custom rule matching on long subdomain labels or high-entropy query names would extend coverage here, linking directly to the DNS tunneling detection project
- Rule tuning was not performed — with 52,000 rules active, production deployments would suppress or threshold high-volume low-value signatures (like the Python BaseHTTP banner) to reduce analyst fatigue
